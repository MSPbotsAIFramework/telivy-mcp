## Requirement understanding

One line: Let Agent platform tenants review external attack surface scans, deep scan risk assessments, and security findings for client tenants via Telivy.

Telivy is a third-party security-scanning vendor (external attack-surface scanning plus an agent-based "deep scan" risk assessment product). The ticket asks for an Agent-platform connector so that an Agent, acting for an MSP tenant, can pull up Telivy's scan inventory, risk-assessment inventory, and the security findings attached to both — i.e. read access to what Telivy already found, not a way to create/modify scans or remediate anything. The `conduit.wyre.ai` link in the description is a reference page for a different product's plugin catalog; it names the same three capabilities (external attack-surface scans, deep-scan risk assessments, security-findings review) and nothing beyond them, so it does not expand scope.

No repo existed for this vendor at the time this ticket first reached design (see "Ticket thread" below); an org admin has since created `MSPbotsAIFramework/telivy-mcp` as an empty scaffold (README only, no implementation). This design treats it as a new connector, first version (SOP main line A).

## Product design

### Goals / Non-goals

**Goals** (v1, matches the ticket's literal ask — read-only review):

- An Agent can list and inspect a tenant's Telivy **external attack-surface scans**: the scan inventory, a given scan's detail, its findings (summary and per-finding detail), and any breach data tied to it.
- An Agent can list and inspect a tenant's Telivy **deep-scan risk assessments**: the assessment inventory, a given assessment's detail and current scan status, the devices under it, device-level findings, the PII-exposure summary, and directory-user exposure (Microsoft 365 or Google Workspace, whichever the assessment covers).
- An Agent can look up the general reference/remediation text for a finding type by its slug, independent of any one scan instance.
- An Agent can pull a risk trend/progress comparison for a scan or assessment across two points in time.
- Every one of the above is scoped to the calling tenant's own Telivy data; one tenant can never see another tenant's scans, assessments, or findings through this connector.

**Non-goals** (explicitly out of scope for v1 — none of these are named in the ticket or the conduit reference page):

- Creating, updating, or deleting an external scan or a risk assessment.
- Triggering a rescan, uninstalling the deep-scan agent, converting a scan to an assessment, ending a trial, or changing monitoring-frequency settings — all of Telivy's write/action endpoints.
- Downloading the PDF/DOCX report binaries — Telivy returns these as raw binary files, not data; piping a multi-MB binary through an MCP tool call does not fit the token-budget contract in §2.5 of the vendor-mcp SOP, and the ticket asks for "review ... findings", which the structured findings/assessment endpoints already serve. See "Decisions made by DEV01" below.
- Fetching Telivy agent-installer version metadata (`/security/agent-versions`) — this serves the deep-scan agent's own installer, not a reviewer of findings; not implied by the ask.

### Acceptance criteria AC1..ACn

All of these are read-only (`readOnlyHint=true`) capabilities exposed as MCP tools. "Given/When/Then" below describes what the Agent observes from the tool call, not the internal implementation.

- **AC1**: Given a tenant's Telivy API key is configured, When the Agent calls the external-scans list tool with no filters, Then it receives a bounded page of that tenant's external scans (each with at minimum: id, organization name, domain, status, created/updated timestamps) plus a total count, and never another tenant's scans.
- **AC2**: Given the same, When the Agent calls the list tool with `search`, `sort_by`/`sort_order`, or `agency_id` filters, Then the returned page reflects those filters (Telivy applies them server-side).
- **AC3**: Given a tenant has zero external scans, When the Agent calls the list tool, Then it receives an empty list and a total of 0 — not an error.
- **AC4**: Given a valid scan id belonging to the calling tenant, When the Agent calls the get-scan-detail tool, Then it receives that scan's full detail.
- **AC5**: Given a scan id that does not exist (or belongs to another tenant's key), When the Agent calls the get-scan-detail tool, Then it receives a structured `not_found` error, not another tenant's data and not a raw exception.
- **AC6**: Given a valid scan id, When the Agent calls the scan-findings tool without a finding slug, Then it receives a summary list of that scan's findings (id, slug, severity, title); When it calls the same tool with a finding slug, Then it receives that finding's full detail for that scan.
- **AC7**: Given a valid scan id, When the Agent calls the breach-data tool, Then it receives that scan's breach records (an empty list is a valid, non-error result when no breach data exists).
- **AC8**: Given a tenant's Telivy API key, When the Agent calls the risk-assessments list tool (with optional `search`/`scan_status`/`sort_by`/`sort_order`/`agency_id`/paging), Then it receives a bounded, filtered page of that tenant's assessments plus a total count.
- **AC9**: Given a valid assessment id, When the Agent calls the get-assessment-detail tool, Then it receives the assessment's detail; When it calls the scan-status tool for the same id, Then it receives the assessment's current scan-status snapshot (a lighter call than the full detail, for an Agent that only needs to know "is it done yet").
- **AC10**: Given a valid assessment id, When the Agent calls the devices tool with no device id, Then it receives the list of devices under that assessment; When it calls the same tool with a device id, Then it receives that device's detail.
- **AC11**: Given a valid assessment id, When the Agent calls the device-findings tool, Then it receives the device-level security findings for that assessment.
- **AC12**: Given a valid assessment id, When the Agent calls the PII-summary tool, Then it receives that assessment's PII-exposure summary.
- **AC13**: Given a valid assessment id and a `provider` of `m365` or `google_workspace`, When the Agent calls the directory-users tool, Then it receives that assessment's user-exposure data for the named provider; When `provider` is anything else, Then it receives a structured `invalid_argument` error.
- **AC14**: Given any finding slug (independent of a scan/assessment instance), When the Agent calls the finding-reference tool, Then it receives the general definition/remediation text for that finding type.
- **AC15**: Given a scan or assessment id, When the Agent calls the risk-progress-report tool with a `current_timestamp_group` (and optionally `compare_with_timestamp_group`), Then it receives the risk trend snapshot (and the comparison, if a second group was given).
- **AC16 (permission/multi-tenant)**: Given a request to `/mcp` that is missing the required Telivy credential header, When any tool is invoked, Then the service returns HTTP 401 before any outbound call to Telivy is made, and the body names the missing header.
- **AC17 (permission/multi-tenant)**: Given two concurrent requests carrying two different tenants' Telivy API keys, When each calls the same list tool at the same time, Then each receives only the data that key is entitled to, with no data from the other request leaking across (no module-level cache, no shared state between the two).
- **AC18 (error handling)**: Given Telivy's API returns 404 / 429 / a 5xx or a network timeout for an upstream call, When the tool handles that response, Then it returns the structured error envelope (`not_found` / `rate_limited` / `upstream_error` respectively) with the correct `retryable` value, and the `message` never contains the raw upstream response body or any credential.
- **AC19 (token economy)**: Given a list-style tool is called with no `limit` or a `limit` above the server's hard cap, When the response is built, Then the effective page size is clamped (default ≤ 50, hard cap ≤ 200) and the serialized response stays within the documented character budget; if the result would exceed it, the tool truncates and sets `has_more=true` rather than silently dropping data or erroring.

### Open questions

- **[not blocking, already assumed]** Whether a Telivy "agency" (the `agencyId` filter Telivy's own API exposes on its list endpoints) maps 1:1 to one MSPbots tenant's API key, or whether a single key can see multiple agencies. Assumed: the API key itself is the tenant boundary (whatever agencies that key is entitled to), and `agency_id` is exposed as an optional **tool argument** (a filter within the key's own scope), not a second credential header — this matches Telivy's API shape (it is a query filter, not a path to a resource the key cannot already reach) and keeps the credential surface to one header per SOP §3.1. If this assumption is wrong (a key can reach agencies outside the calling tenant), AC16/AC17 and the directory-users/PII tools (§7 non-functional, multi-tenant isolation) would need an additional per-tenant allow-list, which the dev leg should flag back to design if it is discovered while building against a real account.
- **[not blocking, already assumed]** The exact field sets Telivy returns per endpoint beyond what the public OpenAPI spec's schema names describe (`ExternalScanDTO`, `RiskAssessmentDTO`, `SecurityFindingDTO`, etc. — the spec gives the DTO names but this design was not able to expand every nested schema). Assumed: the dev leg reads the live OpenAPI spec (`https://api-v1.telivy.com/api-docs/security-json`) at implementation time for exact field names and trims to the subset useful to an Agent (§2.5 field trimming), without needing a second design round — the AC's are written at the capability level (what question can be answered) precisely so this doesn't block.

## Tech design

### Conclusion

Build `telivy-mcp` from scratch per the vendor-mcp-development SOP (main line A, first version): a Python FastMCP Streamable-HTTP service with 13 read-only tools wrapping Telivy's public Security API, one credential header (`X-Telivy-Api-Key`), no write/destructive tools, no report-binary downloads. This is a clean, single-vendor, read-only connector — there is no architectural choice to debate beyond the tool-boundary decisions captured below as "Decisions made by DEV01".

### Where the current implementation lives

Nothing exists yet. `MSPbotsAIFramework/telivy-mcp@main` (8e03cde) is `README.md` only — see "Current state" above. The nearest reference points are other MSPbotsAIFramework vendor-mcp repos built to the same SOP (e.g. the credential-header pattern, FastMCP stateless-HTTP setup, and error-envelope shape are identical across all of them by contract, not by this vendor's choice) — the dev leg should look at one other `*-mcp` repo in the org for the FastMCP scaffolding shape (Dockerfile, `app/` layout) rather than inventing one, per SOP §9 ("Recommended implementation").

### Option analysis

No real alternative to weigh: the vendor-mcp SOP fixes the transport (Streamable HTTP), the credential mechanism (Header per SOP §3.1), the language convention (English-only, SOP §0.4), and the deployment contract (container on the platform's gateway). The only engineering decisions are *which* Telivy endpoints become tools and how they're grouped — covered below in "Decisions made by DEV01", not as a build-vs-buy or library choice.

### Reuse & cleanup

- **Reuse**: FastMCP (`mcp` Python SDK) for the server/tool-registration framework and its `TransportSecuritySettings` for disabling DNS-rebinding protection (SOP §7) — this is the standard base every other vendor-mcp repo in the org uses, not a new dependency choice. An HTTP client library already standard across the org's Python vendor-mcp repos (e.g. `httpx`) for the Telivy client, for its native async support and timeout/retry ergonomics — the dev leg should match whatever the chosen scaffolding reference repo (see "Where the current implementation lives") already uses rather than introducing a second HTTP library into the org's MCP fleet.
- **New dependencies**: the FastMCP/`mcp` SDK and an HTTP client (both already standard for this repo family) are the only expected additions; no new dependency beyond what every sibling vendor-mcp repo already carries. If the dev leg needs a retry/backoff helper, prefer the HTTP client's built-in retry transport over a bespoke implementation.
- **API/method/tool signatures**: tool arguments use plain optional keyword parameters with explicit types/enums (SOP §2.4) — e.g. `provider: Literal["m365", "google_workspace"]`, `sort_order: Literal["asc", "desc"] | None` — rather than a free-form options dict, so the generated JSON Schema constrains the Agent's input. `offset`/`limit` are shared across every list tool with the same default/cap (§2.5), not reinvented per tool.
- **In-scope cleanup**: none — this is a from-scratch repo, there is nothing pre-existing to clean up.
- **Follow-ups (out of scope, flag for a separate ticket)**: a report-export tool (PDF/DOCX) if a future ticket names that need explicitly — see Non-goals for why it's deferred, not dropped for good.

### Data & API contract

**Credential header** (SOP §3.1 table, goes into `README.md`):

| Header | Required | Meaning | Where to get it |
|---|---|---|---|
| `X-Telivy-Api-Key` | Yes | Telivy Security API key, sent upstream as `x-api-key` | Telivy account → API settings |

**Tool catalog** (all `readOnlyHint=true`, `idempotentHint=true`; naming per SOP §2.8, `telivy_<verb>_<resource>`):

| Tool | Args | Wraps (Telivy endpoint) | Returns |
|---|---|---|---|
| `telivy_list_external_scans` | `search?`, `sort_by?`, `sort_order?`, `agency_id?`, `offset?`, `limit?` | `GET /api/v1/security/external-scans` | `{items: [...], total, has_more}` |
| `telivy_get_external_scan` | `scan_id` | `GET /api/v1/security/external-scans/{id}` | scan detail object |
| `telivy_get_external_scan_findings` | `scan_id`, `slug?` | `GET .../findings` or `.../findings/{slug}` | findings summary list, or one finding's detail when `slug` given |
| `telivy_get_external_scan_breach_data` | `scan_id` | `GET .../breach-data` | breach records array |
| `telivy_list_risk_assessments` | `search?`, `scan_status?`, `sort_by?`, `sort_order?`, `agency_id?`, `offset?`, `limit?` | `GET /api/v1/security/risk-assessments` | `{items: [...], total, has_more}` |
| `telivy_get_risk_assessment` | `assessment_id` | `GET /api/v1/security/risk-assessments/{id}` | assessment detail object |
| `telivy_get_risk_assessment_scan_status` | `assessment_id` | `GET .../scan-status` | status snapshot |
| `telivy_list_risk_assessment_devices` | `assessment_id`, `device_id?` | `GET .../devices` or `.../devices/{deviceId}` | device list, or one device's detail when `device_id` given |
| `telivy_get_risk_assessment_findings` | `assessment_id` | `GET .../findings` | device-level findings array |
| `telivy_get_risk_assessment_pii_summary` | `assessment_id` | `GET .../pii-summary` | PII summary object |
| `telivy_get_risk_assessment_directory_users` | `assessment_id`, `provider` (`m365`\|`google_workspace`) | `GET .../m365-users` or `.../gws-users` | directory-user exposure object |
| `telivy_get_finding_reference` | `slug` | `GET /api/v1/security/findings/{slug}` | general finding-type definition |
| `telivy_get_risk_progress_report` | `entity_id`, `current_timestamp_group?`, `compare_with_timestamp_group?` | `GET /api/v1/security/{id}/risk` | trend/comparison object |

13 tools total — under the SOP's "≤20, prefer fewer" guidance (§2.1); list+get pairs that only differ by an optional id (`telivy_get_external_scan_findings`, `telivy_list_risk_assessment_devices`) are merged into one tool per SOP §2.1 ("queries that differ only by parameter become one tool with an optional argument").

**Error envelope** (SOP §4.2, exact vocabulary, no new codes):

```json
{"error": {"code": "not_found", "message": "External scan <id> was not found.", "retryable": false}}
```

`code` ∈ `not_configured | unauthorized | not_found | invalid_argument | rate_limited | upstream_error`. Mapping: Telivy 401/403 → `unauthorized`; 404 on a by-id call → `not_found` (never on a list/search — an empty list is success, per SOP §4.2); 400/422 or a bad `provider` value → `invalid_argument`; 429 → `rate_limited` (`retryable=true`); 5xx/timeout/network error → `upstream_error` (`retryable=true`).

**Backward compatibility**: n/a — first version, no existing clients.

### Key flow / sequence

```
Agent -> Gateway: tools/call telivy_list_external_scans {limit: 20}
Gateway -> telivy-mcp: POST /mcp  (Header: X-Telivy-Api-Key: <tenant's key>)
telivy-mcp: middleware reads header -> 401 early-return if missing (no upstream call)
telivy-mcp -> Telivy API: GET /api/v1/security/external-scans?limit=20  (Header: x-api-key: <tenant's key>)
Telivy API -> telivy-mcp: 200 {data: [...], total: N}
telivy-mcp: trims fields, applies the 20,000-char/has_more budget, serializes compact JSON
telivy-mcp -> Gateway -> Agent: tool result string
```

Error path (Telivy 404 on a by-id call) replaces the last three steps with: Telivy API → `404` → telivy-mcp maps to `{"error": {"code": "not_found", ...}}` → Agent.

### Non-functional

- **Idempotency & concurrency**: every tool is a GET-shaped read with no side effects; safe to retry and safe to call concurrently. Request-scoped `ContextVar` for the credential (SOP §3.3) — no global/module-level variable ever holds a credential or a per-tenant result (SOP §3.4), which is what AC17 tests directly.
- **Performance**: Telivy's own list endpoints default to `limit=100`; this connector re-defaults to `limit<=50` and hard-caps at `<=200` (SOP §2.5) regardless of what Telivy would allow, so one Agent call can't pull an unbounded result set through the gateway.
- **Security**: credential only ever read from the `X-Telivy-Api-Key` header, forwarded upstream as `x-api-key`, never logged, never written to disk, never falls back to an environment variable (SOP §3.1 "never implement a fallback that reads an environment variable when the Header is absent"). Error messages never include the raw Telivy response body (which could itself carry another tenant's org name/domain in a batch error) — see AC18.
- **Multi-tenant isolation**: the API key is the entire tenant boundary (no MSPbots-side tenant id is threaded through) — see the Open Question above on the `agency_id` assumption. No response is ever cached keyed on anything other than (credential-fingerprint, exact request) and the default is no caching at all (SOP §3.4).
- **Observability**: structured log per call — tool name, request-id, Telivy path + status code, duration, error `code` (if any); credentials and response bodies never logged (SOP §6).

### Decisions made by DEV01

No one was available to ask (unattended design run), so the following were decided here; change any of them by commenting and moving the ticket back to `5b - ready for groom`:

- **Read-only v1, no write/action tools** — why: the ticket's ask is "review ... scans, ... assessments, and ... findings" (observation, not action); Telivy's write endpoints (create/update scan or assessment, rescan, uninstall, convert-to-risk-assessment, end-trial, monitoring-settings) are all mutating/irreversible-ish actions against a client's live security posture tooling, and the SOP defaults to read-only absent an explicit business need (§2.7). Alternative not chosen: build the write endpoints too "for completeness" — rejected as unrequested scope with real blast radius (e.g. `uninstall-all` on a client's deep-scan agent).
- **Report-binary downloads (PDF/DOCX) excluded** — why: Telivy returns these as raw binary files; an MCP tool returning a multi-MB binary blob breaks the token-economy contract (SOP §2.5) and isn't something an Agent can usefully consume as tool output. Alternative not chosen: base64-encode the binary into the tool result — rejected, same token-budget problem, just hidden inside a string.
- **`agency_id` is a tool argument, not a second credential header** — why: Telivy exposes it as a query filter on list endpoints, scoped within whatever the API key can already see; treating it as business-level filtering (not a separate credential) keeps the header surface to one field per SOP §3.1's "one credential field, one Header". Alternative not chosen: a second `X-Telivy-Agency-Id` header — rejected unless a real account later shows one key spans multiple agencies and the platform needs to pin a tenant to one of them (see Open Questions / Risks).
- **`telivy_get_external_scan_findings` and `telivy_list_risk_assessment_devices` each merge a list-endpoint and a get-by-id endpoint into one tool via an optional parameter** — why: SOP §2.1 directs merging "queries that differ only by parameter" rather than mirroring every endpoint 1:1; these two pairs are the clearest cases (same resource, same shape, the only difference is "all of them" vs. "one of them"). Alternative not chosen: 13 tools would become 15 if left split — more tools for the Agent to choose between with no added capability.
- **Agent-versions endpoint (`/security/agent-versions`) excluded** — why: it serves the deep-scan agent's own installer/updater, not a reviewer of findings; nothing in the ticket or the conduit reference page implies installer-version visibility is wanted. Alternative not chosen: include it "since it's free" — rejected per YAGNI, it's a 14th tool answering a question nobody asked.

### Deviations from the tech design (implementation details, not product-visible)

1. **`mcp` SDK pinned to `<2`** (tech design's change list didn't specify a version). `mcp[cli]>=1.9.0` alone resolves to `mcp==2.3.0` today, which renamed `FastMCP` to `MCPServer` and removed `mcp.server.fastmcp` entirely (confirmed by import error during setup) — a breaking change the design's reference point (other MSPbotsAIFramework vendor-mcp repos, e.g. `connectsecure-mcp`, lock `mcp==1.28.1`) predates. Pinned `mcp[cli]>=1.9.0,<2` to keep the FastMCP-based scaffolding the SOP and sibling repos actually use; resolved to `mcp==1.30.0`. This is a toolchain-compatibility fix, not a design choice — the moment the org's vendor-mcp fleet moves to the v2 SDK, this repo should move with it.
2. **`provider` parameter typed `str`, not a pydantic `Literal["m365", "google_workspace"]`** as the tech design's "Reuse & cleanup" section suggested as its example of explicit-enum typing. Using a `Literal` here would make FastMCP's own schema validation reject an invalid `provider` value *before* `telivy_get_risk_assessment_directory_users`'s body runs — the agent would see a generic protocol-level validation error, not the `{"error":{"code":"invalid_argument",...}}` envelope AC13/TC-TLV-014 explicitly specifies. Kept `str` with manual validation so the documented envelope contract holds for this one argument. Every other enum-shaped parameter (`sort_by`, `sort_order`, `scan_status`) keeps the `Literal` typing the design called for, since none of those have an AC requiring a specific envelope on a bad value — an upstream `400`/`422` for those (mapped to `invalid_argument` by the client) is sufficient and matches AC18.
